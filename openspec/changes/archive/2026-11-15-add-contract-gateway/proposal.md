# 提案：ApiContract 契约网关（以契约为唯一寻址与治理单位）

## 背景动因
1. **现存业务痛点**：前端调用后端能力时，需要感知服务名、接口路径与实例分布；服务扩容、迁移、灰度都会引起前端改动。后端对外暴露的接口缺少统一的声明与收敛手段，接口级权限、灰度、限流难以实施。
2. **需求来源**：架构设计方案《契约网关.md》v2.0（2026-11-14），来自前端、中台侧通过统一契约标识调用后端能力的整体诉求。
3. **为什么现在落地**：服务与实例规模持续增长，旧模型（契约明细挂载在每实例 metadata）容量受限、网关需遍历实例解析元数据导致 CPU 高企；越晚切换，存量契约越多、迁移与前端改造成本越大。本次 v2.0 一并落地元数据重构、字节码调用、双序列化、异步链路四项改造。

## 当前现状
- 本项目为绿地工程：尚无存量业务代码，`openspec/specs` 无任何已有能力规格，本次为首次引入契约能力。
- 设计方案中描述的**待改造旧模型**（作为对照基线）：
  - 契约明细存放于每个实例的 metadata，各自一份；
  - 网关需遍历实例解析 metadata 才能感知契约，实例与契约规模越大开销越大；
  - 运行期方法调用走反射（`Method.invoke`）；
  - 序列化形态单一（JSON）；
  - 调用链路同步阻塞、频繁建连。
- 外部依赖现状：计划使用 Nacos（Config + Discovery）、Spring Boot 3；注册中心客户端版本由业务统一管理。

## 目标与非目标
✅ 本次目标（可验证、本次必须落地，对齐设计方案 G1–G9）
- 前端只描述契约标识（mt），不感知服务名、接口路径、实例地址（G1）
- 契约唯一定义源在接口层，实现类不承担契约声明职责（G2）
- 契约对外暴露由静态白名单控制，未导出接口在架构层面不可调用（G3）
- 契约元数据与实例地址解耦存储，契约变更与实例上下线互不干扰（G4）
- 运行期调用路径消除反射开销，由启动期生成的调用器完成（G5）
- 传输与序列化可插拔，支持文本与二进制两种形态并渐进切换（G6）
- 网关侧调用链路异步化、连接复用，避免同步阻塞与频繁建连（G7）
- 关键策略（发现、路由、负载均衡、容错、限流、序列化、元数据发布）均可 SPI 扩展（G8）
- 能力以 Starter 形式复用，业务接入只需接口、白名单、实现类三步（G9）

❌ 非目标（明确本次不做，控制范围蔓延，后续迭代）
- 跨语言 SDK 与多语言契约生成
- 契约管理后台、可视化治理平台
- 分布式事务、业务级链路追踪后端
- 服务治理平台的完整权限体系
- 自研二进制私有协议（极限吞吐优化路径，等同重做调用层）
- 面向超高并发的极限性能专项优化
- 网关鉴权与契约级授权（本期不做，仅在过滤器链与 SPI 预留扩展点）
- 前端侧二进制解析能力（前端↔网关固定 JSON；Protobuf 仅用于网关↔Provider 链路）

## 能力清单
### 新增能力
- `contract-definition`：契约定义与导出控制——契约标识声明于接口方法、命名与唯一性约束、导出白名单最小暴露（架构级一票否决）、契约版本与兼容规则
- `contract-metadata`：契约元数据管理——元数据模型与存储布局、先发布元数据后注册实例的顺序不变量、网关订阅与三级索引、多版本共存、冲突与兼容校验
- `contract-provider-invoke`：Provider 契约服务——启动扫描与自检、调用器生成（可降级）、统一泛化入口、参数转换与校验、异常与错误码收敛
- `contract-gateway-routing`：网关契约寻址与路由——mt 解析寻址、实例发现缓存、路由过滤（版本/标签/灰度）、负载均衡、失败容错集群策略、错误码
- `contract-serialization`：契约序列化——JSON/Protobuf 双形态（前端↔网关固定 JSON，Protobuf 仅用于网关↔Provider 链路）、schema 管理、全局/服务/契约三级切换策略与按契约粒度回退
- `contract-async-stability`：异步调用与稳定性——异步非阻塞链路、连接池与背压、三级超时、熔断、契约级限流、调用过滤器链与可观测（日志/指标/traceId 透传/告警）
- `contract-spi-extension`：SPI 扩展机制——扩展点规范（ServiceLoader/@Spi/SpiLoader）、13 个扩展点清单、内置实现与业务覆盖规则
- `contract-starter-access`：业务接入能力——模块划分（api/provider-starter/gateway-starter/bom）、Spring Boot 3 自动装配、配置项体系、三步接入与工程约束

### 修改已有能力
- 无（当前 `openspec/specs` 无存量能力，全部为新增）

## 纳入范围 / 排除范围
### 纳入范围
- **部署形态**：独立网关集群为默认形态（多业务共享、统一治理），保留单机调试模式（本地开发、联调）
- 设计方案第十三节**四个实施阶段的全部交付**（已确认全量纳入）：
  - 阶段一（契约基座）：注解、白名单、Provider 扫描与统一入口、实例标记发布、网关 mt 寻址与轮询负载均衡
  - 阶段二（元数据重构）：元数据迁移至配置中心、网关订阅与三级索引、发布顺序与冲突校验
  - 阶段三（调用与序列化优化）：字节码调用器（可降级）、双序列化 SPI、契约级序列化灰度
  - 阶段四（异步与稳定性）：异步客户端、连接池、三级超时、熔断、限流、过滤器链、审计与指标
- 阶段三与阶段四之间的一次全链路压测检查点
- 工程交付物：`api-contract-api`、`api-contract-provider-starter`、`api-contract-gateway-starter`、`api-contract-bom` 四个模块
- 配置项体系、发布自检日志规范、统一错误码体系、性能验收压测
- 灰度策略：序列化按契约粒度灰度、调用器字节码/反射模式切换、元数据发布方式可回退（nacosConfig / nacosMetadata / logOnly）

### 排除范围
- 与"非目标"一致：跨语言 SDK、治理后台、分布式事务、完整权限体系、自研私有协议、极限性能专项
- 网关鉴权过滤器与契约级授权（本期不做，仅预留过滤器/SPI 扩展点）
- 前端侧 Protobuf 解析能力（前端↔网关固定 JSON）
- 内嵌网关部署形态（后续按需评估）
- 存量数据迁移脚本（绿地工程，无存量数据）

## 依赖项
- **Nacos Config**：契约元数据存储（group=CONTRACT），变更主动推送
- **Nacos Discovery**：服务实例注册、健康检查与实例推送（客户端版本由业务统一管理，Starter 以 provided/optional 声明）
- **Spring Boot 3**：自动装配、条件化装配
- **编译参数 `-parameters`**：契约参数名依赖，缺失时启动告警
- **ASM / ByteBuddy**：启动期字节码调用器生成
- **Reactor Netty**：网关异步 HTTP 客户端与连接池（可选依赖，未引入时降级同步实现并告警）
- **Jackson / Protobuf**：双序列化实现；Protobuf schema 随 `api-contract-api` 依赖分发
- **api-contract-bom**：网关与 Provider 依赖同一版本 `api-contract-api`，统一版本管理

## 待确认问题
无（4 项疑问已在提案评审中闭环，决策记录如下，规格与技术方案阶段须遵循）：
1. **变更覆盖范围 → 全量**：四阶段全部纳入本次变更；阶段三与阶段四之间保留全链路压测检查点。
2. **部署形态 → 独立网关**：独立网关集群为默认形态，保留单机调试模式；内嵌网关形态本期不做。
3. **Protobuf 边界 → 前端不解析二进制**：前端↔网关固定 JSON，Protobuf 仅用于网关↔Provider 内部链路。
4. **鉴权深度 → 本期不做**：不实现网关鉴权过滤器与契约级授权，仅在过滤器链与 SPI 预留扩展点；泛化入口防护依赖内网访问限制与契约级限流。

## 初步风险预判
- **发布顺序不变量**："先发布元数据、后注册实例"若被破坏，出现"实例已上线但契约缺失"中间态（应对：任一步失败中断启动）
- **契约标识冲突**：多服务重复声明同一 mt（应对：发布期聚合索引校验，冲突中断启动）
- **序列化不一致**：网关与 Provider 对同一契约序列化方式不匹配（应对：元数据声明 + 启动校验）
- **白名单静态性**：增量契约需重新扫描或重启（应对：提供重新扫描管理端点，变更纳入发布流程）
- **异步链路复杂度**：回调线程阻塞、超时设置不当引发放大故障（应对：禁止回调阻塞、三级超时统一配置）
- **泛化入口暴露面**：统一入口可调用全部导出契约，且本期不做鉴权（应对：内网访问限制 + 契约级限流 + 过滤器链预留鉴权扩展点）
- **依赖版本漂移**：网关与 Provider 的 `api-contract-api` 版本不一致（应对：BOM 统一 + 发布前兼容性检查）
- 详细风险、降级与回滚方案在 design 技术方案阶段展开

## 验收信号
- **阶段一**：新增契约仅需改接口、白名单、实现类三步，网关零配置即可调用成功
- **阶段二**：契约变更经配置推送秒级生效；网关不再遍历实例解析元数据；单服务契约数突破旧容量限制
- **阶段三**：字节码模式生效且可回退（`api-contract.invoker.mode` 切换）；单契约切 Protobuf 不影响其他契约；压测达到性能目标
- **阶段四**：连接复用稳定、超时与熔断生效、契约级指标可观测、各故障场景均可降级不雪崩
- **发布自检日志**：`export loaded` / `contract ready` / `meta published` / `registry joined` 四项结构化日志齐全，作为上线验收依据
- **性能指标**：网关单机 QPS 不低于优化基线 1.5 倍；P99 在契约级超时内完成、超时率低于 0.1%；契约索引配置推送至生效秒级、刷新期间无请求错误尖刺
